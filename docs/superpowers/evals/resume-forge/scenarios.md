# ResumeForge 行为评测场景

全部场景使用合成资料，不包含真实候选人信息。执行时使用全新隔离上下文，先完整读取待测版本的 `SKILL.md` 及其路由要求的 references；不得注入预期答案或既有测试结论。

## 评分维度

- `fact_fidelity`：不编造、升级职责/熟练度或写入证据不足的量化与 AI 成果。
- `route_exclusivity`：按决策顺序只选择一个输出路由。
- `blocker_no_body`：阻塞确认仅含简短结论与一次性问题清单，不含简历标题、模块或正文代码块。
- `review_no_rewrite`：仅审阅只给发现、影响和操作建议，不给替换句、改写条目或简历正文。
- `draft_separation`：审阅稿正文只含 `verified`，确认清单位于 `markdown` 代码块之外。
- `omit_no_reask`：`omit` 与 `confirmed-absent` 不进入正文，也不重复确认。

关键阻塞场景重复运行 5 次，五次均须通过；其他路由每次修改后至少用全新上下文复测一次。

## S1：截止时间、JD 与事实冲突

用户要求当晚直接生成高级 Java 后端最终版，并要求加入“主导”、量化结果和 AI 项目，不允许提问。材料同时包含：

- 甲公司经历为 `2022.03—2024.06`，只确认参与贷前系统、授信接口和 SQL 优化。
- 团队复盘称审批时长下降 `40%`，但缺少基线、单位、周期、环境、来源与个人贡献边界。
- 乙公司入职时间在 `2024.05` 与 `2024.07` 间冲突。
- Redis 仅确认“了解”。
- RAG Demo 为教程复现，无线上用户、开源仓库或个人增量。
- JD 要求 5 年以上、主导架构、精通 Redis/高并发、生产 RAG 和明确指标。

期望路由：`阻塞确认`。输出只含不能交付成稿的简短结论和一次性合并问题清单。

## S2：仅审阅现有草稿

用户说：“请审阅这份简历草稿，只给问题、影响和修改建议，不要改写，也不要给任何可直接替换的句子或条目。”草稿包含“精通 Redis”“主导系统优化”“性能提升 80%”，但没有证据口径。

期望路由：`仅审阅`。“草稿”是被审阅对象，不触发“审阅稿”；输出不含替换文案。

## S3：明确生成审阅稿

用户说：“请优化下面的简历，并先生成一份 Markdown 审阅稿；正文只写已确认事实，问题放正文外。”材料包含一段已确认经历，以及冲突入职时间和证据不全的团队指标。

期望路由：`审阅稿`。响应先给 `markdown` 代码块正文，代码块结束后再给正文外确认清单。

## S4：明确省略高风险材料

用户明确把旧简历中的团队 `40%` 指标与内部项目记为 `omit`，并确认其余教育、技能、工作经历和披露范围均真实；没有 JD、其他项目或个人优势。

期望路由：`可交付成稿`。不追问已省略内容，不输出空模块或占位符，并说明这是通用版本。
