# 图示与闭环规范

流程图是对已冻结事实的结构化表达，不是补全未知业务的手段。凡存在操作流程、状态变化、跨端交互、跨服务调用或长链路，必须绘制与实际复杂度匹配的 Mermaid 图，并在图旁说明图覆盖的范围、触发条件和异常边界。

## Mermaid 选择规则

| 需要回答的问题 | 必选图形 | 使用要点 |
| --- | --- | --- |
| 系统边界、模块或服务依赖 | 架构图 | 采用与事实匹配的 Mermaid 图，标出边界、数据归属和中间件，不画未确认组件。 |
| 多参与方按时间交互 | `sequenceDiagram` | 参与方、调用顺序、同步返回、异步投递及错误返回必须与接口和正文一致。 |
| 条件分支、失败和恢复 | `flowchart` | 表达判定、分支、重试、补偿、转人工和回到可恢复状态的路径。 |
| 状态与合法迁移 | `stateDiagram-v2` | 表达状态、触发条件、守卫、终态和非法迁移拒绝；不要混入页面或消息状态。 |
| 实体、主外键和基数 | `erDiagram` | 表达实体关系、基数和逻辑关联；字段细节仍以数据库字段表为准。 |

一个图无法清楚表达所有维度时组合使用：架构图说明边界，时序图说明主链路，流程图说明异常和恢复，状态机说明生命周期，实体关系图说明数据关联。长链路至少有时序图或流程图；存在状态迁移时同时提供状态机；分布式或异步链路应让服务、中间件、数据库和消费者出现在同一条可追踪链路中。

## 闭环单元

每条业务、服务或全栈交互链路以以下九项为最小闭环单元：

`触发 → 主体 → 调用方行为 → 接口 → 服务处理 → 数据/中间件变化 → 返回 → 反馈 → 恢复`

“主体”是用户、定时调度、消息消费者、外部回调方或服务；“反馈”是页面、上游服务、消息消费者或运维人员可观察到的结果；“恢复”说明失败、中断、重复或竞争后的责任方和可执行动作。同步返回不代表闭环完成，仍需说明结果消费和后续状态。

| 闭环项 | 必须回答的问题 |
| --- | --- |
| 触发 | 什么条件、事件或操作开始链路？ |
| 主体 | 谁触发，具有什么身份、权限或调度资格？ |
| 调用方行为 | 如何组装请求、等待、投递、轮询或显示状态？ |
| 接口 | 使用哪个 URL、方法、事件或回调契约，前置与幂等是什么？ |
| 服务处理 | 哪个模块或服务验证、编排并推进何种状态？ |
| 数据/中间件变化 | 哪些表、缓存、消息、任务或外部资源何时变化？ |
| 返回 | 返回值、确认或消费结果是什么，错误如何传播？ |
| 反馈 | 调用方、页面或消费方如何展示、继续或停止？ |
| 恢复 | 重试、补偿、刷新、重新进入、对账或人工介入如何发生？ |

## 反向与并发路径

每条适用链路除了主成功流，还要逐项确认并图示或在图旁对应说明：无权限或身份失效、参数或业务校验失败、重复请求或重复消息、并发修改或状态竞争、下游超时或不可用、数据库与消息等部分成功、页面或任务中断后的恢复。某项确实不适用时说明不适用依据；不允许仅以“统一异常处理”省略行为。

部分成功必须明确已完成部分、未完成部分、对外返回、后续重试或补偿和最终收敛责任。并发场景必须明确竞争对象、控制机制和失败方的反馈。中断恢复必须说明恢复入口和数据来源，不能只写“支持重试”。

## 一致性审查

在落盘前逐项审查：

1. 需求覆盖：每项影响设计的需求能定位到设计章节、链路、接口、数据影响和验收场景。
2. 接口闭环：每个调用方动作有接口，每个接口有服务处理、数据影响、结果消费方、错误处理和后续动作。
3. 数据状态闭环：关键字段和状态具有生产者、消费者、进入和退出条件、合法后继状态及失效或归档语义。
4. 前后端对齐：页面操作、状态、字段、校验、防重、刷新恢复、错误提示与后端契约逐项一致。
5. 命名和图文一致：图中的参与方、接口、实体、字段、状态和顺序与正文、字段表、示例完全一致；新增名称标为新增设计定义。

图中每个箭头、节点和分支必须能在正文、接口或数据模型中找到依据；正文描述的关键参与方、状态变化和异常恢复也必须能在适当图中追踪。不要用 Mermaid 的注释或示例名称制造未确认事实。
