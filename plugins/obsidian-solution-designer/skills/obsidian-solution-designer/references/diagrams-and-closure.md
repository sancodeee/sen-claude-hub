# 图示与闭环规范

Mermaid 是对已冻结事实的结构化表达，不是补全未知业务或装饰文档的手段。只有当参与方顺序、条件分支、合法状态迁移或实体关系无法由短表清楚表达时才绘图，并在图旁说明覆盖范围、触发条件和异常边界。模板不预置固定图形数量。

## Mermaid 选择规则

| 可观察条件 | 选择图形 | 使用要点 |
| --- | --- | --- |
| 多模块、服务或数据归属难以从职责表看清 | 架构图 | 标出边界、数据归属和真实中间件，不画未确认组件；简单单体优先只保留职责表。 |
| 三个以上参与方存在重要顺序、同步返回或异步衔接 | `sequenceDiagram` | 参与方、调用顺序、同步返回、异步投递及错误返回必须与接口和正文一致。 |
| 分支、失败和恢复路径无法在 `FLOW-xx` 中简洁说明 | `flowchart` | 表达判定、分支、重试、补偿、转人工和回到可恢复状态的路径。 |
| 存在受约束的业务或页面状态迁移 | `stateDiagram-v2` | 表达状态、触发条件、守卫、终态和非法迁移拒绝；页面状态与业务状态分别绘制。 |
| 多实体关系或基数影响实现设计 | `erDiagram` | 表达实体关系、基数和逻辑关联；字段细节仍以 `DATA-xx` 为准。 |

一个图只回答一个主要问题。只有两个维度都达到上表选择条件时才组合图形；不要为同一简单链路同时绘制时序图和流程图。长链路也先判断参与方顺序或分支是否无法由导航表与 `FLOW-xx` 清楚表达，达到条件后才选择时序图或流程图；存在重要状态迁移时再增加状态机。分布式或异步链路无论是否绘图，都必须让服务、中间件、数据库和消费者在闭环导航与正文中可追踪。

## 闭环导航与编号

正式文档维护一张闭环导航表。表格可以合并列，但表头和每行必须覆盖场景、触发与主体、调用或接口、服务处理、数据或状态变化、返回或反馈、异常恢复和验收。每行以 `FLOW-xx` 开头并引用 `AC-xx`；涉及接口、数据或统一错误策略时引用 `API-xx`、`DATA-xx`、`ERR-xx`。

每个编号只能定义一次，定义必须是以编号开头的 H2–H6 标题，例如 `### API-01：查询接口`；表格或行内编号只算引用。定义必须包含已核验正文或至少一行真实表格数据，空标题、空表、裸 callout、HTML 注释或只有 Mermaid 图不算实质内容。`FLOW-xx` 是行为闭环的唯一完整定义；API、数据、错误恢复和验收在各自章节定义后由其他位置引用。闭环导航只做短摘要和跳转，不复制详细内容。

## 闭环单元

每条 `FLOW-xx` 以以下九项为最小闭环单元：

`触发 → 主体 → 调用方行为 → 接口 → 服务处理 → 数据/中间件变化 → 返回 → 反馈 → 恢复`

“主体”是用户、定时调度、消息消费者、外部回调方或服务；“反馈”是页面、上游服务、消息消费者或运维人员可观察到的结果；“恢复”说明失败、中断、重复或竞争后的责任方和可执行动作。同步返回不代表闭环完成，仍需说明结果消费和后续状态。

| 闭环项 | 必须回答的问题 |
| --- | --- |
| 触发 | 什么条件、事件或操作开始链路？ |
| 主体 | 谁触发，具有什么身份、权限或调度资格？ |
| 调用方行为 | 如何组装请求、等待、投递、轮询或显示状态？ |
| 接口 | 使用哪个 URL、方法、事件或回调契约，前置与幂等是什么；若为本地动作，边界和不涉及接口的依据是什么？ |
| 服务处理 | 哪个模块或服务验证、编排并推进何种状态？ |
| 数据/中间件变化 | 哪些表、缓存、消息、任务或外部资源何时变化？ |
| 返回 | 返回值、确认或消费结果是什么，错误如何传播？ |
| 反馈 | 调用方、页面或消费方如何展示、继续或停止？ |
| 恢复 | 重试、补偿、刷新、重新进入、对账或人工介入如何发生？ |

## 反向与并发路径

每条适用链路除了主成功流，还要在 `FLOW/ERR` 正文或表格中逐项确认：无权限或身份失效、参数或业务校验失败、重复请求或重复消息、并发修改或状态竞争、下游超时或不可用、数据库与消息等部分成功、页面或任务中断后的恢复。只有已经选择相关图形时，才同时在图中对应表达。某项确实不适用时说明不适用依据；不允许仅以“统一异常处理”省略行为。

部分成功必须明确已完成部分、未完成部分、对外返回、后续重试或补偿和最终收敛责任。并发场景必须明确竞争对象、控制机制和失败方的反馈。中断恢复必须说明恢复入口和数据来源，不能只写“支持重试”。

## 一致性审查

在落盘前逐项审查：

1. 需求覆盖：每项影响设计的需求能定位到 `FLOW`、`AC`，以及实际涉及的契约、数据影响和错误策略。
2. 接口闭环：每个调用方动作有接口或明确本地动作，每个真实接口能引用服务处理、实际数据或资源影响、结果消费方、错误处理和后续动作。
3. 数据状态闭环：实际涉及的关键字段和状态具有生产者、消费者、进入和退出条件、合法后继状态及失效或归档语义；不涉及持久化时有可核验依据。
4. 前后端对齐：页面操作、状态、字段、校验、防重、刷新恢复、错误提示与后端契约逐项一致。
5. 命名和图文一致：编号唯一且引用可解析；存在图时，图中的参与方、接口、实体、字段、状态和顺序与正文、字段表、示例完全一致；新增名称标为新增设计定义。

存在图时，每个箭头、节点和分支必须能在正文、接口或数据模型中找到依据，图所覆盖的关键参与方、状态变化和异常恢复也必须可追踪。未绘图的场景以导航表与正文完成一致性审查。不要用 Mermaid 的注释或示例名称制造未确认事实。
