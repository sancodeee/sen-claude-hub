# trip-forge 多代理保真协议 · 方案（已落地，存档）

> 状态：**已于 v1.7.0 落地**，实现见 `../skills/trip-forge/references/multi-agent.md` 与 `SKILL.md` 的「多 Agent 增强模式」。本文件保留为设计动机与原理存档。与方案的主要差异：质检拆为 Consistency Review + Final Verification 两个只读闸门；调研域切五类而非四类；事实文件命名为 `<目的地>-<出行首日>-research.md`。
> 关联代码：`plugins/trip-forge/skills/trip-forge/`（SKILL.md / references/multi-agent.md / references/template.md / assets/report-template.html）。

---

## 1. 背景：要解决的不是"慢"，是"长任务信息失真"

单 agent 跑完整 trip-forge 是一条很长的链：

```
读规范 → 9 类联网调研（天气/车票/机票/地图/门票/住宿/餐饮/潮汐/避坑）
       → 选景评分定级 → 六维度 + 景点详情卡分段生成 → 合并校验
```

上下文一路累积。模型能力有限时，越到后期越容易：

- 把前面**核实过的精确数字**（车次号、票价、营业时间、天气数值）记串；
- 在记忆模糊处**凭印象编造（幻觉）**，把 ⚠️/❓ 的信息当成既定事实写出；
- **行程不合理**：点位顺序折返、时段冲突、某天超载、餐饮不顺路、跨城衔接对不上。

目标是**提质**——保证信息准确 + 行程合理。手段是用多 agent 做**上下文隔离**，对抗长任务退化。

## 2. 关键认知：多 agent 不会自动保真，分配才是难点

> 多 agent **不解决**失真——切分和交接设计不当，信息照样在子代理之间走样。

所以本方案的核心不是"分几个角色"，而是**怎么分、怎么交接才不失真**。它由「一个核心机制」+「五条保真原则」支撑，角色只是其上的执行单元。

## 3. 核心机制：调研事实文件（single source of truth）

所有调研结论一律落盘到一个结构化事实文件，而非憋在某个 agent 的上下文里。

- **位置**：`travel-guides/<目的地>-research.md`（中间产物，默认保留以便复核回溯，可删）。
- **统一 schema**（复用 `template.md` 的「来源附录」表结构，使其同时直接生成最终 HTML 的来源附录）：

  | 信息项 | 结论 / 原始数值 | 来源（🏛️/🛒/💬） | 核验日期 | 置信度 ✅/⚠️/❓ | 备注 |
  | --- | --- | --- | --- | --- | --- |
  | 例：G1087 北京南→烟台 | 11:22→16:33，二等座约 300+ | 🏛️ 12306 | 2026-06-15 | ⚠️ | 周末早订 |

- **铁律**：生成阶段所有易变数字**从事实文件照抄**，**禁凭记忆改写**；无法核实的只能按 ❓ 写，下游不得脑补成确定值。

> 价值：真相的唯一来源是磁盘文件，不是任何 agent 的对话记忆。这条**即便维持单 agent 也应启用**——是最廉价、最关键的防失真手段，与现有「分段写入文件解决截断」一脉相承（现在再加「事实落盘解决失真」）。

## 4. 多代理分配的保真五原则

1. **MECE 信息域切分（不按流程切）**——每个子代理拥有一个完整自洽、互不重叠的信息域，域内自己完成「调研 + 交叉核验两处 + 达详细度下限 + 标置信度」，避免一份信息经多手传递走样。
2. **结构化交接，禁散文转述**——子代理只往事实文件写 schema 字段 + 返回极简完成摘要，不返回「印象式」自然语言结论。
3. **保真锚点是落盘文件，不是对话记忆**——跨 agent 传递的是文件里的结构化事实。
4. **置信度随值走**——来源 + 核验日期 + 置信度绑定每个数值，传到哪带到哪；❓ 不得在下游被「升级」为确定。
5. **独立复核闭环**——质检子代理用**新上下文**比对成稿 vs 事实文件，抓数值漂移 / 幻觉 / 行程不合理。

## 5. 角色设计（克制；生成阶段始终由主代理单线程写 HTML，规避写同一文件冲突）

| 角色 | 上下文 | 职责 | 产出 |
| --- | --- | --- | --- |
| **领域调研子代理 ×4** | 隔离、并发 | 默认切：①交通 ②食宿 ③景点+天气 ④避坑。域内联网核实 + 交叉两处 + 达详细度下限 + 标置信度 | 写入事实文件 + 极简完成摘要 |
| **主代理** | 主线 | 读事实文件 → 按「四++ 选景决策」评星定级 → 单线程分段写 HTML（易变数值照抄事实文件） | 成稿 HTML |
| **质检子代理 ×1** | 新上下文、只读 | (a) 成稿数值 vs 事实文件逐条一致、无新增未核实信息（反幻觉）；(b) **行程合理性**（动线不折返/时段不冲突/每天不超载/餐饮就近顺路/跨城衔接合理/星级与排程一致）；(c) 交付检查清单 + 禁废话 | 问题清单 → 主代理修正 |

> 为什么生成阶段不并行：SKILL.md 要求逐段追加写入**同一个 HTML 文件**，多 agent 并发写会互相覆盖；且选景→行程表→详情卡之间有依赖。并行只放在「只读、独立、无写冲突」的调研与质检环节。

## 6. 降级路径（兼容 Claude Code 与 Codex）

子代理工具（Task/Agent）不可用时（如 Codex 端）→ 退回主代理顺序执行（即现状流程），但**仍落盘事实文件并自我复核一遍**。SKILL.md 全程用「若子代理工具可用…否则…」措辞，不破坏现有单线程路径。

## 8. 实施触发条件（满足任一即值得动手）

- 单 agent 成稿里出现**数值漂移**：报告中的票价/车次/营业时间与调研时不一致。
- 出现**幻觉**：把未核实信息当既定事实，或编造不存在的店名/班次。
- **行程不合理**反复出现：点位折返、时段冲突、某天超载、餐饮不顺路、跨城衔接对不上。
- 行程越长（≥5 天 / 多城市）问题越明显——说明确是上下文退化所致。

若单 agent 表现稳定，则**只采纳第 3 节「事实文件」机制**（低成本、单 agent 也适用），多代理部分继续搁置。
