# 创建与清理失败后的恢复

仅在脚本失败、部分成功或目标状态与预期不符时读取。

## 创建已生成 worktree，但复制配置或写基线失败

`create_incomplete` 表示目录和分支已保留，配置可能只复制了一部分，基线可能缺失。先做只读检查：

```bash
git -C "<source_repo>" worktree list --porcelain
git -C "<target_dir>" status --porcelain=v1 --untracked-files=all --ignored
git -C "<target_dir>" rev-parse --git-dir
```

根据报错检查对应配置路径的存在性和权限，或磁盘空间；不输出配置正文。基线位于最后一个命令返回的 Git 元数据目录中的 `git-worktree-helper-baseline.json`。

向用户报告已创建的目录、分支、失败阶段以及基线是否存在。先解决实际错误；不要对同一路径重新执行创建、覆盖分支、自动删除已生成内容，也不要重新采集当前状态作为创建基线，以免把后续变更错误地当成初始状态。

- 用户要保留使用：沿用已有 worktree，说明缺失的配置；仅在用户授权的范围内补齐缺失项，不覆盖现有内容。无可信创建基线时继续使用无基线保守回收，不能声称初始化完整成功。
- 用户要回收：使用清理脚本默认模式。缺失基线按旧 worktree 保守比较；配置冲突仍阻断，不能用强制删除解决。
- 用户未明确选择且选择影响现有文件时，只询问保留使用或安全回收，不自行替用户决定。

## 配置写入中途失败

清理脚本会保留目标 worktree，但先前成功回收的文件可能已经写入主项目。先修复权限或空间问题，重新运行默认清理；相同结果会跳过，不手动回退主项目，也不伪造基线。

## 清理期间检测到变化

`config_sync_changed` 表示配置与计划快照不一致，`worktree_changed` 表示 HEAD、分支或非受管脏路径集合变化。两者都不能通过 `--force` 绕过。

先暂停其他编辑器、代理或进程的写入，检查主项目和目标 worktree 的实际变更，再重新运行默认清理。同步已经完成的文件可能留在主项目，新写入仍保留在目标；不要自动回滚、覆盖新增内容、更新基线或直接删目录。若重新预检产生配置冲突，按正常冲突流程处理。

这些检查属于状态复核，不是文件系统锁；在最后一次检查与 Git 删除之间继续写入仍有风险，因此不能一边编辑一边清理。

## 目录删除成功，分支删除失败

结合输出中的 `REMOVED worktree`、`DELETED branch` 和只读 worktree/分支查询确认实际状态。报告“目录已删除、分支保留”及原因；不要把整个操作视为完全未执行，再对已删除目录盲目重跑，也不要绕过脚本执行 `git branch -D`。

## 参数或 Git 命令失败

退出 `1` 不保证没有副作用。先区分参数校验失败、创建部分成功、清理部分成功，再报告下一步。

- detached HEAD 且未指定基准：取得用户需要的基准引用后再创建。
- 目录或分支已存在：保留现有状态，核实是否为此前部分成功；需要新名称时再询问，不覆盖。
- 目标不是已注册 worktree：检查目标与所属仓库是否正确，不强制。
- 无法识别的异常：保留输出及现有文件，说明未完成步骤；不临场替换为更强的 Git 命令。
