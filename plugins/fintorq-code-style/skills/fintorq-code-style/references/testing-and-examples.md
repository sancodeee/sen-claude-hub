# 测试、文档与实现模式

## Javadoc 与注释

- Service 接口、Mapper 方法、Controller 对外方法应说明方法职责、参数、返回值和重要异常。
- 实现类的普通 `@Override` 方法不重复接口 Javadoc；新增 public/protected 方法及非显然的 private 方法按相邻代码补充说明。
- 注释解释原因、约束和兼容背景，不逐句翻译代码。
- TODO 必须写清待解决问题和触发条件，不能作为缺失实现的长期替代。

## 单元测试

使用当前项目的 JUnit 5、Mockito 和既有测试基建。

- 测试类默认命名 `*Test`，测试方法优先使用 `method_scenario_expectedResult`。
- 测试可观察行为，不只验证 mock 调用次数；静态 mock 使用 try-with-resources。
- 对本次技术实现覆盖适用的成功、异常、资源释放和兼容路径；修复工程缺陷时先写能够复现问题的测试，保留现有测试行为。
- 业务字段的范围、空值处理、状态和业务错误期望由需求及既有契约决定，不由本 Skill 规定或验收。异常实现测试可断言已有异常类型、结构化错误码传递或原因链，不判断具体业务场景应该触发何种业务错误。
- 不为了让测试容易通过而在生产代码中增加测试专用分支。

## 常用实现模式

### 属性复制与审计字段

属性映射沿用当前接口与实体的既有实现方式，只显式复制已允许外部修改的属性；服务端控制字段由项目既有的可信机制维护，不能被外部 DTO 覆盖。不将固定排除字段清单当作通用安全模板，也不由本 Skill 决定业务上可编辑的字段集合。

主键及审计机制先按 [`persistence-and-permissions.md`](persistence-and-permissions.md) 核验。若 `createBy`、`updateBy` 为必填，应按项目现有方式从可信身份上下文设置。若对应表、Mapper 或 `MetaObjectHandler` 已提供审计字段，遵循实际机制，避免重复覆盖；否则按当前字段类型设置必要审计值，`Date` 字段可使用 `Date.from(Instant.now())`。主键生成与回填同样以当前持久化路径为准。

新增或更新的判定、记录不存在时的处理及状态流转遵循当前业务契约，不由本 Skill 规定统一流程。

### 分页转换

优先使用 `IPage.convert` 保留页码、页大小和总数：

```java
IPage<LoanLeadDbVO> dbPage = mapper.getLoanLeadPage(page, queryDTO);
return dbPage.convert(this::convertToVO);
```

### 异步任务

使用项目管理的线程池，不直接创建不可控线程。异步失败必须记录足够上下文或传播给调用方。

## 验证

先确定验证对象，再按最小充分原则选择验证：

- 本插件的 Markdown、JSON 和入口改动：检查结构、引用、元数据一致性和规范范围回归场景，执行 `git diff --check`；不为验证插件去运行另一个 Fintorq 业务仓库的测试。
- Java 实现改动：先列出受影响的技术行为及对应测试类或方法，再选择下列检查。规范审查不运行姓名长度、手机号格式等业务规则验收测试。确有必要确认实现方式或技术兼容性时，仍应定向运行相关测试；不因已有业务断言或业务测试失败而改写业务规则。
- 按覆盖行为选择测试，不只看测试类名。混合测试类中直接验证本次异常映射或兼容路径的方法仍应运行；工具支持时按方法筛选，无法拆分时说明同次执行中的相关与无关结果。

1. 文档或清单：如果仓库或插件提供对应校验器则运行，并执行 `git diff --check`。
2. 纯类型、签名或依赖调整：运行受影响模块的 `compileJava`；签名影响调用方时同时编译消费者。异常传递、校验触发、资源释放、SQL 生成等技术行为变化，应运行直接相关的定向行为测试；编译成功不能替代技术行为验证。
3. 公共模块或跨模块修改：补充受影响消费者的编译及直接相关技术测试。
4. Spring 配置、构造器或 Bean 依赖变化：运行能够创建相关 ApplicationContext 的测试；必要时验证启动链路。
5. 异常路由或 API 技术契约变化：按 [`api-security-and-errors.md`](api-security-and-errors.md) 核对实际 Advice 作用域及优先级，运行相关 MVC/契约测试，并确认调用方技术兼容。
6. 数据权限框架接入变化：验证注解参数、主表与别名匹配、路由及既有 fail-closed 机制；不以业务授权范围正确性为规范验收条件。

代码规范结论以是否遵循项目代码约定为依据，不以业务测试成败为通过条件。验证报告分别说明规范检查、编译和相关技术测试的实际结果。已观察到的业务测试失败应另行如实列明测试名、失败内容、与本次改动的关联及已核实的修改前基线；未核实归因时明确标记。不得将其改称为插件规范失败，也不能隐去失败后笼统声称全部测试通过。用户另行要求业务实现或验收时，将对应业务测试结果单独报告。

未经用户在当前任务中明确同意，不运行 Testcontainers、Docker 依赖测试、全量 `tc*` 任务或 `--rerun-tasks`。无法运行必要校验时，明确说明原因和剩余风险。
